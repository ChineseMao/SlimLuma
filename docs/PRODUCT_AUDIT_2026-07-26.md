## 结论

SlimLuma 现在已形成图片、动画图片、视频和 PDF 的本地批量压缩闭环，并补齐本轮
竞品调研中优先级最高的剪贴板导入、文件夹监控、Finder 入口和压缩前后对比。实现
仍坚持同一边界：SlimLuma 负责安全工作流，成熟第三方引擎负责压缩算法。

这不等于与任一竞品“功能完全对齐”。当前闭环的是高频导入、批处理、设置、压缩、
完整性验证、结果与历史路径；目标体积、逐文件参数、视频暂停/剩余时间、音频专项等
仍是明确的后续扩展。本文记录代码、测试和文件回归结果，不把尚未执行的运行时 UI、
Finder 服务或快捷指令人工验收写成已验收。

本轮最重要的变化不是“再多几个开关”，而是把结果可信度做成硬约束：

- qpdf 与 Ghostscript 同时可用时，PDF 先由 qpdf 修复结构，再由 Ghostscript
  压缩，最后由 qpdf 线性化；缺少其中一个时按公开的后备路径执行。
- 页数变化，书签、链接/批注、表单、签名字段数量减少，加密状态改变、可搜索文本
  大幅塌缩，或支持线性化的路径未兑现设置时，临时输出会被丢弃；PDFKit 不具备的
  线性化不会被伪装成成功，也不会被误报为文件损坏。
- PDF 这层是数量与状态信号守门，不会证明链接目标、书签目的地、表单行为或每一页
  渲染语义完全等价；视觉结论只覆盖实际抽样页。
- 动画图片会逐帧解码，并比较帧数、逐帧时长和循环设置；当前只允许安全的保持格式
  或 WebP 转换。
- 视频用 ffprobe 验证容器、时长及音视频/字幕轨道，AVFoundation 只提供系统预览
  兼容性信号，因此有效 MKV / WebM 不会因 Quick Look 不支持而被误拒绝。
- 所有输出仍先写隐藏临时文件，验证通过后才移动到最终路径。

## 本轮发现与修复

### P0：PDF 可以打开，但不代表结果正确

代表性私有 Sample C 的页数正常、文本仍可搜索，却丢失了原有书签。旧验证只检查
“PDFKit 能打开且页数大于 0”，因此错误输出会被当成成功。现在比较压缩前后的结构
数量与状态信号，发生已覆盖的退化会停止落盘并显示具体的前后数量。

### P0：勾选“网页快速打开”却没有生效

旧 Ghostscript 参数没有启用线性化，三个已生成的 PDF 都显示 `Optimized: no`。直接
依赖 Ghostscript `FastWebView` 对复杂文件又可能产生有问题的线性化数据。现在 qpdf
可用时在 Ghostscript 后执行 `qpdf --linearize`；仅有 Ghostscript 时由其尝试生成。
只要实际后端声明支持线性化，“必须线性化”就会进入输出验收条件。

### P0：异常输入需要先修复再压缩

Sample C 原文件的名称树存在错误。直接交给 Ghostscript 会丢失书签；先经过 qpdf
结构修复后，页数和书签都能保留。在 qpdf 与 Ghostscript 同时可用的回归环境中，
最终链路为“修复 → 压缩 → 网页优化 → 完整性检查”；任何中间步骤出错都不会进入
历史结果。

### 验证边界：PDF 结构守门不是全内容等价证明

当前自动检查覆盖页数、书签数、链接/批注数、表单字段数、签名字段数、加密状态、
可提取文本规模与线性化状态。它能捕获本轮真实出现的“书签全部丢失”等严重
退化，但不逐项比较书签目的地、链接目标、批注内容、表单脚本或页面像素。

本轮视觉检查是在相同分辨率下抽样 Sample A、B、C 的代表性页面；因此只能表述为
“抽样页未发现肉眼可见的错位或缺失”，不能推导为三个 PDF 的每一页都完成视觉验收。

### P1：动画图片不能只验证第一帧

旧逻辑只解码第 0 帧。实测 GIF 转 JPEG/PNG 会拆成多个文件，转 HEIC/AVIF 还可能
改变播放时序。现在会在处理前阻止不安全转换，并在处理后逐帧解码；帧数相同但每帧
时长被调换、某帧时长元数据缺失，或循环次数丢失/改变，也会拒绝输出。

### P1：AV1 不能假设固定编码器存在

旧路径固定请求 `libaom-av1`，但常见 FFmpeg 构建可能只提供 `libsvtav1`。现在任务
开始前读取当前 FFmpeg 编码器列表，优先使用 `libsvtav1`，其次使用
`libaom-av1`；两者都没有时解释如何更新 FFmpeg 或切换 H.264 / HEVC，不会启动一个
注定失败的进程。

视频完整性检查也改为以配套 ffprobe 为准，比较时长及视频、音频、字幕轨道。这样既
能验证真实容器内容，也不会把 AVFoundation 无法预览的有效 MKV / WebM 当成损坏。

FFmpeg 与 ffprobe 现在作为一个 readiness 单元：只有两者同时存在才显示“可用”。
若找到 FFmpeg 但同目录没有 ffprobe，工具页显示“部分失效”，安装按钮会走
`brew reinstall ffmpeg` 补齐 companion；复制恢复命令也使用同一重装路径。

### P1：嵌套完整性错误不能在非中文界面漏回中文

图片帧数/时序、视频轨道/时长和 PDF 多项结构风险可能嵌套在“输出文件验证失败”里。
现在会拆分风险子句并按当前 locale 本地化，保留数量等诊断值；文件名等用户数据仍
原样呈现。专项测试覆盖英文 PDF/动画错误及阿拉伯语视频错误，防止外层翻译后内层
仍残留中文。

### P1：自动任务在忙时不能丢失启动请求

剪贴板或文件夹监控可能在当前批次仍在执行时加入新文件。现在会记录待自动开始状态，
当前批次收尾后立即检查队列并续跑；取消操作会同时清除此状态，避免用户取消后又自动
启动。

### P1：“重新处理”不应要求用户再点一次开始

批次结束后点击“重新处理”会先同步把已完成、未生成、失败或取消项恢复为等待状态，
随后在同一操作中调用启动逻辑并立即进入处理态，避免界面只完成重置、还要用户第二次
点击“开始压缩”。

### P1：监控防循环规则必须随输出设置变化

仅在启动监控时计算一次输出目录和后缀，会在用户修改设置后失效。现在输出位置、
自定义目录或文件名后缀改变时会刷新监控配置，但不会把已存在文件重新当作新文件。
扫描会忽略自定义输出目录、当前规范化后缀及旧版 `-slim` 后缀。

### P1：图片“无损”和系统后备必须诚实

无损开关现在只允许 PNG、WebP，以及保持原格式时的 GIF、TIFF、BMP、JPEG 2000
等兼容格式；JPEG、HEIC、AVIF 会在任务开始前拦截。这里的“无损”指编码路径，
如果同时设置缩小尺寸或清理元数据，输出仍会按这些显式设置改变。

ImageMagick 缺失时不再把 `sips` 当作完全等价的替代品。只有当前任务选择“移除定位
和拍摄信息”、关闭 ICC 保留，且输出格式/无损要求能由系统后备兑现时才继续；否则
在写出前停止并提供 ImageMagick 安装入口。`sips` 路径会分别计算宽、高约束，不再用
一个最长边近似两个独立限制。

“全部移除元数据”和“保留 ICC”也不再互相冲突：发现嵌入 ICC 时先提取色彩配置，
使用 `-strip` 清理注释、属性和其余配置，再恢复 ICC。真实 JPEG 集成测试同时断言
ICC 仍存在且敏感注释已经消失。

### P1：PDF 后备能力与设置必须一致

- qpdf 的非无损模式会让“图片质量”参与符合条件的内嵌图片重编码，但不会改变图片
  DPI，也不能执行灰度转换。
- 图片 DPI 和灰度只在实际使用 Ghostscript 时生效；其余路径会禁用这些控件并解释
  原因。
- PDFKit 后备只做有限无损重写，不支持网页线性化。勾选“网页快速打开”时会明确
  提示本次未应用；完整性检查只对实际支持线性化的引擎要求该结果，避免把能力缺失
  误判为 PDF 损坏。
- 自动模式的“无损整理”只优先 qpdf；qpdf 缺失时使用 PDFKit，即使机器已安装
  Ghostscript 也不会让有重写语义的 Ghostscript 冒充无损后备。显式选择
  Ghostscript 的无损档位会关闭图片重编码、降采样和灰度参数。

### P1：外部进程启动失败也必须清理受管状态

`ProcessRunner` 在调用 `Process.run()` 前登记任务，以支持统一取消。现在即使可执行
文件不存在、启动阶段直接抛错，`defer` 仍会解除 stdout/stderr 回调并从活动进程表
移除该任务；回归测试断言启动失败后活动进程数为 0，避免后续取消或重试命中幽灵任务。

### P1：文件级操作不应放在窗口全局工具栏

右上角“添加”和垃圾桶看起来像对整个 app 生效，而且与页面内添加入口重复。现在
添加、剪贴板导入和“清空队列”都放在“媒体压缩 → 文件队列”内；单文件移除、打开、
Finder 定位和前后对比放在对应行。

### P1：灰底控件缺少可操作感

图片、视频、PDF 与“应用预设”原本位于连续灰背景上，容易被理解为禁用说明。现在
媒体类型使用有边框、有图标、有勾选和高亮选中态的按钮；预设是标准菜单按钮；参数卡
与页面画布分层，状态不再只依赖灰度和颜色。

## macOS 交互闭环

- 使用 `NavigationSplitView`、原生 sidebar、List、Form、Menu、文件面板、拖放、
  Quick Look 和 Services。
- 添加/清空属于队列，移除/比较/打开属于单个文件，安装属于引擎页。
- Finder 可通过“服务 → 添加到 SlimLuma 压缩队列”或“打开方式”导入文件；
  macOS 15 及以上还提供可传入文件并选择是否自动开始的原生快捷指令动作。
- 主工作区采用单窗口 `Window(id: "main")`，AppKit 与 SwiftUI 的打开事件汇入同一
  `AppState`，并对短时间重复路由去重。代码路径预期连续打开两个 PDF 时只保留一个
  主窗口并加入同一队列；目前没有本轮运行时截图或实机操作证据，仍待解锁目标 Mac
  验收，当前只能视为静态实现结论。
- 自动化页集中管理剪贴板行为、监控文件夹、递归扫描、已有文件和自动开始策略。
- 默认不覆盖原件、不保留变大的输出；失败、跳过和安全拦截都会进入本地历史。
- 压缩前后对比有可见“关闭”按钮，并支持 Escape；对比中的 Finder 操作会在结果
  被移动或删除时给出错误，不会静默失效。
- 从菜单或快捷键添加文件后会切回“媒体压缩”并把主窗口带到前台；清空队列需要
  二次确认，失败或未生成的历史记录也可以重新加入队列。
- 大文件剪贴板导入有进行中、正在取消和取消完成状态；“取消全部”会同步停止导入
  与扫描，之后的自动化批次不会重新处理刚被用户取消的旧任务。
- 主窗口关闭或退出时如果仍在压缩、导入、扫描或安装引擎，会要求用户选择“继续使用”
  或“取消任务并退出”，退出前会终止受管外部进程。
- 清空队列、清空历史和删除自定义预设均提供明确的破坏性操作与“取消”按钮；任务
  菜单同时提供 `Command-Return` 开始压缩与 `Command-.` 取消当前批次。
- 队列、历史和引擎状态把装饰图标从辅助功能树中隐藏，并为引擎行合并朗读“可用 /
  部分失效 / 未安装”、缺失组件以及路径或恢复命令，减少 VoiceOver 重复信息。
- App Intent 使用原子回执完成冷启动交接，不再依赖可能挂起的结果对话框；取消的
  导入会消费回执并清理精确批次，暂存根、批次和文件都拒绝符号链接。
- 运行中的监控选项变更不会再次导入已有文件；状态区会区分“运行中”“部分失效”和
  “需要处理”，避免全部目录失效时仍显示绿色成功。

以上是实现层面的交互结构检查。窗口观感、控件命中区、键盘焦点、VoiceOver、
Finder 服务和快捷指令入口仍需在解锁的目标 Mac 上做运行时人工验收。

## 已闭环与下一阶段

本轮已闭环：

1. 图片、视频、PDF 混合导入 → 有界并发 → 临时输出 → 类型专属完整性检查 →
   唯一结果文件 → 本地历史。
2. 拖放、剪贴板、文件夹监控、Finder/打开方式与 App Intent 的代码接入，其中
   自动导入在忙时可续跑，监控规则会动态防止处理自身输出。
3. 引擎探测、Homebrew 安装、缺失能力解释，以及设置与实际后端能力的对应关系。
4. 代表性私有 PDF 样本的结构缺陷定位与新链路真实文件回归。
5. FFmpeg + ffprobe 联合 readiness、缺 companion 的一键重装恢复，以及外部进程
   启动失败清理。
6. “重新处理”同步重置并启动，以及嵌套完整性错误的多语言输出路径。

后续扩展：

1. 更多快捷指令参数与批次结果回传。
2. 视频编码级进度、剩余时间与暂停。
3. 目标体积迭代压缩和逐文件参数覆盖。
4. 字幕事件级内容/时序验证，而不只比较字幕轨道数量。
5. 音频专项压缩与动画首帧/逐帧导出模式。
6. 解锁目标 Mac 上的 UI、Finder、快捷指令、键盘与辅助功能验收。
7. Developer ID 签名、公证和正式分发。
