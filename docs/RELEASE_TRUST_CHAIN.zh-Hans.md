# SlimLuma 发布信任链

正式发布不是一个“签名”按钮，而是一条互相补位的信任链。每一层回答的问题不同：
是谁发布、文件有没有被改、Apple 是否扫描过、离线 Mac 能否验证，以及 GitHub 上
下载到的是否正是通过验证的那一份。

## 权限、证书与验证

| 环节 | 为什么需要 | 没有时会怎样 | 完成后解决什么 |
| --- | --- | --- | --- |
| Keychain 私钥访问 | `codesign` 必须用只由发布者持有的私钥生成签名。授权只给签名工具，不把私钥导出到仓库或日志。 | 只有公开证书也无法签名；导出并到处复制私钥则会扩大冒用风险。 | 证明签名由持有发布私钥的一方生成，同时让私钥继续受 macOS Keychain 保护。 |
| Developer ID Application 证书 | Apple 用证书把公钥、法定发行主体和 Team ID 绑定起来。SlimLuma 根据私有发布策略精确核对两者。 | ad-hoc 或无证书构建不能建立可信发布者身份，Gatekeeper 会警告或阻止。 | 用户可在签名详情中确认发布者，Apple 也能撤销被盗或滥用的证书。 |
| Hardened Runtime | 公证要求应用启用受保护的运行时，并限制常见代码注入、动态库替换和调试绕过。 | 公证可能拒绝，应用在运行时也缺少重要系统防护。 | 把签名时的完整性保证延伸到应用运行阶段。 |
| 安全时间戳 | Apple 时间戳服务器证明签名发生在证书有效期内。 | 证书日后到期时，系统更难判断旧签名当时是否有效；长期验证可能失败。 | 即使证书后来正常到期，已发布版本仍可按签名时状态验证。 |
| 严格签名验证 | `codesign --verify --strict` 检查主程序、嵌套代码和资源封装是否在签名后被改动。 | “执行过签名命令”不代表最终包仍完整，复制或打包步骤也可能破坏签名。 | 在上传前发现篡改、遗漏签名或打包损坏。 |
| Universal 架构验证 | `lipo` 分别确认 `arm64` 和 `x86_64`，而不是只相信文件名。 | 某一类 Intel 或 Apple Silicon 用户下载后无法运行，或被迫依赖 Rosetta。 | 同一个发行包原生覆盖两类 Mac。 |
| 禁止调试 entitlement | 正式包不得带 `get-task-allow` 等开发调试能力。 | 其他进程更容易附加或读取应用；Apple 公证也可能拒绝。 | 把开发权限从公开发行物中移除。 |
| Apple 公证认证 | `notarytool` 的 Keychain profile 或 App Store Connect API 凭据只用于向 Apple 证明“谁有权提交”。 | 无法上传或查询公证任务；把凭据写入命令、源码或日志会造成账户风险。 | 在不把密码、私钥嵌入应用的前提下提交扫描。SlimLuma 当前复用本机 Keychain profile，不需要仓库中的 `.p8`。 |
| Apple 公证 | Apple 对已签名的精确字节执行恶意软件与签名策略检查，并签发 ticket。 | Developer ID 签名只能说明发布者，不能说明 Apple 已检查；Gatekeeper 可能显示“无法检查恶意软件”。 | Apple 为该精确构建给出 `Accepted` 记录。App、CLI 归档与 DMG 分别验证，不能相互替代。 |
| Staple | 把 Apple ticket 附到 App 或 DMG 上。 | 联网时系统可能在线查询成功，但离线、网络受限或 Apple 服务异常时验证可能失败。 | 用户无需联网也能验证公证状态。裸 CLI 没有可 staple 的容器，以 Apple `Accepted` 加严格签名为准。 |
| Gatekeeper 验收 | `spctl` 按最终用户的 macOS 安全策略检查 App/DMG。 | 公证成功后仍可能因容器、签名嵌套或分发方式错误而无法打开。 | 证明最终交付形态能通过 macOS 的实际启动门禁。 |
| SHA-256 | 校验和给下载文件一个公开、可复算的指纹。 | 镜像传输损坏、缓存错包或附件被替换时，用户无法独立发现。 | 用户可确认下载字节与发布者公布的附件一致；SHA-256 不替代代码签名。 |
| 匿名重新下载验证 | 从公开 Release 重新下载，避免只验证本机构建目录里的文件。 | CI 绿灯或上传成功仍可能伴随 404、权限错误、错版本或错附件。 | 证明普通访客看到的下载链接、文件名、哈希、签名、公证和版本都正确。 |
| Git commit / tag 的 SSH 签名 | 发布者用本机 SSH 私钥签名提交与 tag；仓库只保存公开签名公钥。 | 未签名或未知签名人的 tag 会被发布工作流拒绝；把私钥上传 GitHub 或仓库则会让别人冒充发布者。 | 把源码提交、版本 tag 和经过授权的发布者绑定起来，不接触 Developer ID 私钥。 |
| GitHub 最小权限 | 构建、签名和公证 job 只用 `contents: read`；只有不接触 Apple 私钥的 publish job 短暂获得 `contents: write`。 | 完全没有写权限就不能创建 Release；把写权限给编译或第三方工具步骤，则其中任一步被攻破都可能修改仓库或附件。 | 让每个 job 只拥有完成自己职责所需的最小权限，并把 Apple 凭据与 GitHub 写权限隔离。 |
| 受保护的 release environment | 自动发行时，P12、密码与 Apple API 凭据只由受保护环境交给签名 job，可附加人工审批。 | 没有凭据无法签名或公证；把它们放入普通源码、PR job 或日志会扩大泄露面。 | 把敏感凭据限定到明确的发行事件。当前本机发行使用 Keychain profile，不把这些值上传仓库。 |
| main / tag 保护 | `main` 禁止未审核强推，发行 tag 禁止更新或删除，发布环境只接受受保护来源。 | 已验证的代码或 tag 仍可能在上传前被替换，造成检查对象与公开附件不一致。 | 固定 CI、签名、公证和 GitHub Release 所引用的同一组字节与提交。 |
| 受保护分支上的 signed tag 验证 | 发布工作流必须从受保护的 `main` 加载固定 signer 列表，并确认 tag 的提交已经合并到 `main`。 | 如果从 tag 自身读取 signer 列表，攻击者可以同时替换代码和“信任根”；如果不检查祖先关系，正确签名但未经评审的旁支提交仍可能发行。 | 把“谁签的”“代码是否经过 main 的 CI/评审”和“实际构建的 tag”绑定成一条可审计链路。 |

## 哪些信息公开，哪些必须保密

最终签名必然允许 macOS 向用户显示法定签名主体、Team ID、Developer ID 证书链、
bundle ID 与版本，公开校验和、许可证和发布签名公钥也必须可验证。为减少不必要的
搜索索引和关联，仓库文本不再重复法定主体和 Team ID；精确匹配值只保存在私有发布
配置中。

必须保密的包括 Developer ID 私钥与 `.p12`、P12 密码、App Store Connect `.p8`
私钥、Apple 专用密码、Keychain 密码、GitHub token、公证 submission ID 与个人
路径。仓库只可出现 secret 的变量名，不得出现值。`.cer` 与证书签名请求本身通常
不含私钥，但仍应只作为本地运营文件管理。

## SlimLuma 当前发布边界

- 本机 Keychain 中的 Developer ID 私钥用于签名，私钥不导出到项目；
- 本机 Keychain 公证 profile 用于提交，认证值不进入应用、Git 或 Release；
- GitHub 自动发行默认关闭；只有 release environment、保护规则和 secrets 均已配置
  后才允许显式开启；
- 构建关闭发行调试信息、移除本地符号，并拒绝含本机用户路径的 Mach-O；
- CLI archive 把所有者元数据规范化为公开的系统身份，不保存本机用户名；
- 加密 PDF 的明文中间件只进入 `0700` 私有工作区，任务结束清理，后续启动会清理
  SlimLuma 自有的陈旧目录；
- GitHub Release 发布后还要进行匿名下载复验，完成前不能宣称正式发行。
